## 附：笔速上限钳制（2026-11-14 试跑后修，非"去妆"内容）

试跑标定采集页时发现：同样两笔拖拽，HUD「峰值」显示 **38367 px/s**。原因是 `inst = dist / dt` 只有 `dt > 0.001 && dt < 1` 的保护，指针事件间隔可低到 1 ms 而位移上百 px，`dist/dt` 直接上万。手写画不出这个速度，但它会：

- 抬高 20 s 滚动窗口峰值 → 之后几乎所有采样点都满足"掉落"条件 → `cliffRatio` 系统性偏低（实测那份文件里掉落比例中位只有 **0.07**）；
- 让断崖门槛 300 px/s 失去意义：相对一个假峰值判断"掉得狠不狠"，等于换了把尺；
- EMA 0.72/0.28 会把一个尖峰带进后面几十个采样点，一个抖动污染一整段。

修法：两处同一套公式都加物理上限 `SPEED_CAP = 3000` px/s（900 px 画布上，手最快也到不了），`Math.min(dist / dt, SPEED_CAP)` 之后再进 EMA。

- `标定/笔速标定采集页.html`（采集结果，直接影响标定数据）
- 本原型 `board` 的 `pointermove`（影响 HUD 峰值显示与实时断崖判定）

验证：同样的两笔拖拽，峰值 **38367 → 844**，全部采样点落在 cap 内；两文件抽取脚本 `node --check` 均通过；采集页导出的 JSON（900×600、15 s、57 采样点、2 落笔）能被 `标定_分位分析.mjs` 正常读入并算出分位。两个试跑文件已从 `D:\Downloads` 删除，机器上无残留。

注意：`LEVEL_PROFILES` 三档数值**未改**，仍是设计取值；这次只修了算法漏洞，不动数字。
