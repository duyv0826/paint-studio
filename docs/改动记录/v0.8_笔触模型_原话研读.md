# 「检测笔触」到底是什么 —— 交互设计概论这批录音的逐条核对

> 一句话：**产品不是一个「让你在里面画画」的软件，也不是一个「判断你在不在画」的计时器。
> 它从系统输入流里把每一笔切出来（落笔—轨迹—抬笔—撤回），用这一笔的形态和节奏，判断你有没有在认真画。**
> 「笔触」是它的数据单位；番茄钟是容器；自习桌是压力的出口。三者不是一回事。

## 二、我之前的三个误读（明确记下来，免得再犯）

1. **把「监测」窄化成「有没有在动」。**
   v0.6 / v0.7 的判断主力是「停笔 20s → 提醒」。这条能跑，但它只回答「人还在不在」，
   没有回答「在不在认真画」。原话要的是后者（1:36:28「检测你有没有在认真画画」），
   而证据链只能来自**每一笔的形态**，不是「最后动的时间」。

2. **把「笔触」等同于「压感」。**
   我在 v0.7 说明里写「笔压/倾角读不到，别写进报告当功能」。这句把「笔触」缩成了「力度」。
   原话里的笔触（2:27:53）紧跟着的是**撤回步数、笔数、每分钟**——这三样都是**时序与几何**，
   从指针轨迹就能还原。压感是笔触的**一部分**（更细的那层），不是全部。

3. **用词让人误解成「要在我这个软件里画」。**
   「在我画的软件里落笔就开始计时」这句话读起来像「你得在我这儿画」。
   原话 2:27:03 和 2:27:46 把这条钉死了：不在它里面画，只从外面监测。

另外补一句：**「笔触」这个词在整批录音里只出现一次**（2:27:53，而且是「笔触之类的」这种附和）。
所以严格说，它不是讲话人给的定义，而是三个更硬的锚点推出来的结论——
1:35:16 的「笔速」、2:27:22 的「读鼠标轨迹」、12 号 1:12:18 的「朋友敲键盘，猫就敲键盘」。
把这个词当定义用可以，但报告里要写清是**推论**，别写成「他说要检测笔触」。

## 三、「笔触」在系统里的可计算定义（三层）

### 第 1 层：输入流（原始信号）
| 信号 | 来源 | 频率 |
|---|---|---|
| 指针坐标 | `GetCursorPos` | 30 Hz |
| 笔尖按下/抬起 | `GetAsyncKeyState(VK_LBUTTON)` 边沿 | 30 Hz 采样 |
| 撤回 | `GetAsyncKeyState(VK_CONTROL) ∧ VK_Z` 边沿 | 30 Hz 采样 |
| 前台程序 | `GetForegroundWindow` + 进程名 | 2 Hz（0.5s 缓存） |

数位板在这个层面就是鼠标（原话 2:27:22 的判断是对的，Windows 的笔输入默认映射成鼠标事件）。

### 第 2 层：笔触（一笔一记）
一次落笔 → 抬笔 = 一条笔触记录：

| 字段 | 含义 | 为什么值得记 |
|---|---|---|
| `t0 / t1 / dur` | 起笔、收笔、这一笔花了多久 | 长笔触＝铺色/长线；0.2s 的笔触＝点、勾、试探 |
| `path` | 轨迹长度（px） | 「画了多少」的真实单位，比「点了几次」稳 |
| `avg_v / peak_v` | 笔内平均/峰值速度 | 原话点名要的「笔速」 |
| `pauses` | 笔内停顿次数（悬笔 >0.25s） | 停顿多＝在找形/犹豫，和「流畅」是两种状态 |
| `straight` | 弦长/轨迹长（0–1） | 接近 1＝直线/长线；接近 0＝反复涂抹 |
| `x0,y0 / x1,y1` | 起止点 | 能算「这一笔落在画面哪一块」 |
| `undo` | 这一笔在 3 秒内被撤回 | **撤回不是孤立事件，它归属于某一笔** |

### 第 3 层：判断（从笔触到「认不认真」）
现有 + 可算的派生量（都已进 JSON）：

| 聚合 | 公式 | 读法 |
|---|---|---|
| 笔触数 | `stroke_count` | 产量 |
| 均笔触 / 中位笔触 | `mean/median(path)` | 是在「画」还是在「戳」 |
| 短笔触占比 | `path<20px 的比例` | 高＝点状试探/乱涂，低＝成形的线 |
| 撤回率 | `undos / stroke_count` | 高＝画废/反复改；对应原话「撤回步数」 |
| 笔触间隔中位数 | `median(t0_i - t1_{i-1})` | 起笔之间的空档 |
| 节奏离散度 CV | `std(gap)/mean(gap)` | 稳＝持续输出；散＝走走停停 |
| 笔内停顿总数 | `Σ pauses` | 犹豫密度 |
| 笔速/峰值 | 见上 | 原话点名要的 |

**判断逻辑因此从「停笔 x 秒」升级为「停笔 x 秒 或 笔触形态塌了」。**
第二类信号（形态塌陷）我**没有**自作主张加进提醒，因为阈值没有依据；字段先落地，等你的真实数据。
这是刻意的：先把证据收集对，再谈判定，否则就是拍脑袋。

## 五、现在证明得了什么、证明不了什么

**证明得了**
1. 小窗能读到系统级指针（不是页内画布），前台不在绘画软件时不计数。
2. 一笔能被切成一条记录，撤回能归属到具体的笔。
3. 笔速、笔数、每分钟、撤回率这些原话点名的量，都能从输入流直接得到，**不需要接软件、不需要授权**。

**证明不了（必须写进报告的 limitations）**
1. **真实数位板落笔是否等同左键**——只能你本人拿笔画一次验（`--probe 20`，画十笔看 `strokes`）。
2. **压感/倾角/笔刷参数**：读不到。想要「力度笔触」，得走 Raw Input 订阅 HID 数位板报文（`RegisterRawInputDevices` + `RIDEV_INPUTSINK`），
   这条能做，但工作量约一天，而且不同品牌的报文不一致——**不是这次交付的内容**，是「笔触还有下半截」的明确缺口。
3. 撤回只认 `Ctrl+Z`；PS 里 `Ctrl+Shift+Z`（重做）不算，SAI/CSP 改键会漏。
4. 任何「左键拖动」都长得像落笔：选色、拖图层、涂蒙版都会被算成一笔。前台白名单挡住浏览器，挡不住绘画软件内部的非绘制操作。
5. 同桌仍是本机演示；联机没做。
6. 「屏幕共享给同桌看」这条（12 号 1:11:39 的参考产品行为）没做，而且**原话里并没有要求**——它只是被当作参考产品的能力提到过。要不要做，是产品决策，不是原话要求。

## 六、下一场（11/14 14:00）拿三个数，别拿问卷

1. **笔触准不准**：让对方在自己常用的软件里画 3 分钟，人工数一遍，和 `stroke_count` 对差多少（差 >10% 就说明切笔逻辑要改）。
2. **撤回率**：`undo_rate` 和对方主观「今天改得多不多」对不对得上。
3. **压力反应**：被提醒/被问号之后，下一笔隔多久（`delay_ms`、`reaction_ms`）。

这三个数决定后面怎么写 RQ 的效度部分；问卷只会给你「感觉还行」。
